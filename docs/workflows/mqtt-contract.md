# Workflow: MQTT contract

The MQTT message format is a **stable contract** between daikintomqtt and downstream integrations (primarily **daikinRCCloud** for Jeedom). Breaking changes require coordinated updates in both repos.

## Base topic

Configured in `settings.yml` → `mqtt.topic` (default: `daikinToMQTT`).

All paths below are relative to `{baseTopic}/`.

## Published topics (retained, QoS 0)

| Topic | Payload | When |
|-------|---------|------|
| `{deviceId}` | JSON device state | On change (or always if `publishOnDelta: false`) |
| `jeedom/{deviceId}` | JSON array of Jeedom CMD definitions | When `integration.jeedom: true` |
| `{INSTANCE_ID}` | JSON SystemBridge state | On system events |
| `system/bridge/availability` | `"online"` / LWT `"offline"` | Connect / disconnect |
| `system/bridge/{key}` | string | Config values via `publishConfig()` |
| `{discoveryPrefix}/{component}/{objectId}/config` | JSON HA discovery | When HA enabled (absolute path, not prefixed) |

`INSTANCE_ID` = `960adb71-4632-4f53-bf47-8ffa5abd7581` — **must stay identical** in daikinRCCloud PHP.

## Subscribed topics (commands)

| Topic | Payload | Handler |
|-------|---------|---------|
| `{deviceId}/set` | JSON `{ "_key": value, ... }` | Coalesced → `applyGatewayEvents` |
| `{INSTANCE_ID}/set` | `{ "refreshAllDevices": true }` or `{ "_refreshAllDevices": true }` | Full cloud refresh |
| `system/bridge/refresh/set` | Legacy refresh | Same as above |

## Device state payload shape

```json
{
  "_onOffMode": "on",
  "_setpointTemperature": 22,
  "_device": {
    "id": "...",
    "name": "...",
    "modelInfo": "BRP069C42",
    "supportStatus": "full"
  },
  "_supportStatus": "full",
  "_configCoverage": "complete"
}
```

Rules:
- **State keys** = `propertyKey` from characteristic definitions (always `_` prefix)
- **`_device`** = device metadata object (required by Jeedom plugin)
- **Support fields** (`_supportStatus`, `_configCoverage`, `_unmappedDatapoints`, `_debugReport`) = consumed by daikinRCCloud for diagnostics

## Jeedom command definitions (`jeedom/{deviceId}`)

Generated by `generateCMD()` in `converter/jeedom.ts`. Each entry has:

| Field | Description |
|-------|-------------|
| `logicalID` | Matches state key (e.g. `_onOffMode`) |
| `type` | `info` or `action` |
| `subType` | `numeric`, `string`, `binary`, `slider`, `select`, `other` |
| `name` | Display name |
| `generic_type` | Jeedom generic type (optional) |

### Action suffix conventions (required by daikinRCCloud)

| Characteristic type | Info logicalID | Action logicalIDs |
|--------------------|----------------|-------------------|
| Binary (settable) | `_mySwitch` | `_mySwitch_ON`, `_mySwitch_OFF` |
| Numeric (settable) | `_setpoint` | `_setpoint_Slider` |
| String/enum (settable) | `_operationMode` | `_operationMode_Select` |

The action's `value` field points back to the info logicalID. daikinRCCloudCmd strips the suffix and publishes `{ "_propertyKey": value }` to `{deviceId}/set`.

**Do not change these suffix patterns** without updating daikinRCCloud.

## Incoming command format

Publish to `{baseTopic}/{deviceId}/set`:

```json
{ "_setpointTemperature": 21 }
```

Keys may be sent with or without `_` prefix — normalized in `eventValue()`.

## Special commands (CharacteristicWriter.ts)

| Key | Effect |
|-----|--------|
| `_triggerFirmwareUpdate: true` | Trigger firmware update flow |
| `_setPresetAway: true` or `"away"` | Set away preset |
| `_{zone}_scheduleEnabled` | Enable/disable schedule for zone |

These are handled before standard characteristic lookup. New special commands must be documented here and tested.

## DynamicGateway key format

When `DynamicGateway` is used, keys follow:

```
_{embeddedId}_{dataPoint}_{pathSegment}
```

Example: `_climateControlMainZone_onOffMode`

Static gateways use curated `propertyKey` names from `catalog.ts` — prefer static naming when adding mappings.

## Breaking vs safe changes

### Safe (no daikinRCCloud change needed)

- Adding new `_propertyKey` fields to device state
- Adding new entries to `jeedom/{deviceId}` array (auto-creates Jeedom commands)
- Adding new support metadata fields
- Changing internal cloud API mapping while keeping same MQTT keys

### Breaking (requires daikinRCCloud update)

- Renaming or removing existing `logicalID` / `propertyKey`
- Changing action suffix conventions (`_ON`, `_OFF`, `_Slider`, `_Select`)
- Changing `INSTANCE_ID`
- Changing base topic structure or `/set` payload format
- Changing `_device` object shape expected by Jeedom plugin
- Protocol V3 (commented in PHP as future `handleMqttMessageV3` for daemon >= 3.0.0)

## Verification

After MQTT-related changes:

1. `npm run build`
2. Run relevant unit tests
3. If adding characteristics: `node test/unit/apiCoverageAudit.test.js`
4. Manually verify Jeedom command creation if integration format changed

See also: [mapping-datapoints.md](../mapping-datapoints.md) for adding fields that publish over MQTT.
